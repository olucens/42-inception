## Блок A — Что такое контейнер

**A1.** **namespaces** — изоляция (что процесс видит), **cgroups** — лимиты
(сколько может потребить), **union filesystem / OverlayFS** — послойная
файловая система (свой root fs без копирования).
*Критерий 100%: все три + различие «видит» / «потребляет» / «файловая система».*

**A2.** PID namespace изолирует пространство идентификаторов процессов. Первый
процесс в новом namespace получает PID 1 внутри него, при этом на хосте у него
обычный большой PID — одно ядро, разные нумерации. Внутри процесс не видит
процессы хоста.
*Критерий 100%: изоляция ID + двойная нумерация (внутри 1, снаружи другой) + невидимость чужих процессов.*

**A3.** `mount` — таблица монтирований и своё дерево ФС; `net` — интерфейсы,
маршруты, порты, iptables; `uts` — hostname и domainname; `ipc` — очереди
сообщений, разделяемая память, семафоры; `user` — отображение UID/GID (root
внутри = непривилегированный снаружи); `cgroup` — вид на иерархию cgroups.
*Критерий 100%: пять штук с корректным «что изолирует».*

**A4.** cgroups ограничивают и учитывают потребление ресурсов: CPU, память, I/O,
число процессов. Namespaces отвечают на «что процесс видит», cgroups — на
«сколько процесс может взять». Без cgroups изолированный процесс всё равно
съел бы всю память хоста.
*Критерий 100%: ресурсы + явное противопоставление namespaces + следствие.*

**A5.** lowerdir — слои образа, read-only, стопкой. upperdir — writable-слой
контейнера. merged — то, что видит процесс: объединение, где верхнее перекрывает
нижнее. При изменении файла срабатывает copy-on-write: файл целиком копируется
из lower в upper и правится там. Удаление создаёт whiteout-файл в upper; в lower
оригинал остаётся.
*Критерий 100%: три каталога + copy-on-write + whiteout при удалении.*

**A6.** Writable-слой удаляется вместе с контейнером. Для БД это потеря всех
данных при любом `docker rm`, пересоздании контейнера, обновлении образа.
Поэтому `/var/lib/mysql` обязан быть на томе.
*Критерий 100%: данные исчезают + перечислены обычные операции, при которых это происходит.*

**A7.** ВМ виртуализирует железо: гипервизор даёт виртуальные CPU/диски/NIC, и на
них грузится полноценная гостевая ОС **со своим ядром**. Контейнер — процессы в
изменённом представлении **того же** ядра хоста. Граница изоляции у ВМ —
гипервизор, у контейнера — интерфейс системных вызовов ядра.
*Критерий 100%: своё ядро против общего + названы обе границы изоляции.*

**A8.** У контейнера ничего не грузится: не проходит BIOS/UEFI, не стартует ядро,
не поднимается init и системные сервисы. Запускается один процесс в новых
namespace'ах. У ВМ каждый из этих шагов реально выполняется.
*Критерий 100%: «нет загрузки ОС» + перечисление того, что именно пропускается.*

**A9.** Когда граница должна выдерживать враждебный код. Поверхность атаки
контейнера — весь syscall-интерфейс ядра (сотни вызовов), и уязвимость в ядре даёт
побег на хост и во все соседние контейнеры. У гипервизора интерфейс на порядок
уже. Отсюда мультитенантные облака: ВМ между клиентами, контейнеры внутри клиента.
*Критерий 100%: размер поверхности атаки + «побег через ядро» + пример применения.*

**A10.** Ядро одно — хоста, и контейнер лишь получает другой вид на него. Бинарник
для другого ядра просто нечему исполнять. На macOS и Windows Docker поднимает
скрытую Linux-ВМ, и все контейнеры работают внутри неё; «контейнеры на macOS» —
это контейнеры на Linux в ВМ.
*Критерий 100%: общее ядро + вывод о невозможности + скрытая ВМ на macOS/Windows.*

## Блок B — Образы и Dockerfile

**A11.** Слой — зафиксированный набор изменений ФС от одной инструкции, read-only,
со своим хешем. Слои складываются в OverlayFS. Удаление в *следующем* слое
создаёт whiteout: файл скрыт в merged, но байты остаются в предыдущем слое и
едут в образе. Чистить надо в том же `RUN`, что и создавал.
*Критерий 100%: слой неизменяем + whiteout скрывает, но не удаляет + вывод про «в том же RUN».*

**A12.** `CMD` — команда по умолчанию, легко переопределяется аргументами
`docker run`. `ENTRYPOINT` — то, что выполняется всегда; аргументы `docker run`
становятся *аргументами* для него. Контейнер-как-приложение → ENTRYPOINT,
контейнер-как-среда → CMD. Вместе: ENTRYPOINT — программа, CMD — её аргументы по
умолчанию.
*Критерий 100%: переопределяемость + поведение аргументов + связка ENTRYPOINT+CMD.*

**A13.** Shell-форма выполняется как `/bin/sh -c "команда"`: PID 1 — это sh, а
программа — его ребёнок. Exec-форма запускает бинарник напрямую, он и есть PID 1.
Для ENTRYPOINT критично: sh не пересылает сигналы детям, поэтому SIGTERM от
`docker stop` до демона не доходит.
*Критерий 100%: sh -c обёртка + кто PID 1 + следствие с сигналами.*

**A14.** `ARG` существует только во время сборки, в готовом образе его нет. `ENV`
доступна и при сборке, и в рантайме, и **сохраняется в метаданных образа** — её
видно в `docker inspect` и в `docker history`.
*Критерий 100%: время жизни каждой + «ENV видна в образе».*

**A15.** Значение `ARG` попадает в метаданные слоя, где он использовался.
`docker history --no-trunc <образ>` покажет команду вместе с подставленным
значением. Пароль утёк ко всем, у кого есть образ, даже если в файловой системе
его нет.
*Критерий 100%: попадает в историю слоя + названа команда + «образ = утечка».*

**A16.** `COPY` копирует файлы из build context, и всё. `ADD` дополнительно
распаковывает локальные архивы и умеет скачивать по URL. `COPY` предпочтительнее
потому, что предсказуем: `ADD` может неожиданно распаковать архив, который ты
хотел положить как файл.
*Критерий 100%: обе доп. способности ADD + аргумент про предсказуемость.*

**A17.** `EXPOSE` — метаданные: документирует порт, виден в `docker inspect`,
используется `-P` для случайного маппинга. Он **не** публикует порт на хост и
**не** влияет на доступность между контейнерами: в общей сети порт доступен и
без него.
*Критерий 100%: метаданные + оба «не».*

**A18.** Docker кеширует результат каждой инструкции; при изменении инструкции
инвалидируются она и **все последующие**. `COPY . /app` меняется при правке
любого файла проекта, поэтому `RUN apt-get install` после него будет
переустанавливать пакеты при каждой правке кода. Редко меняющееся — выше.
*Критерий 100%: каскадная инвалидация + конкретное следствие + правило порядка.*

**A19.** Build context — всё, что демону отправляет клиент перед сборкой.
Без `.dockerignore` туда уедет `.git`, `node_modules`, локальные `.env` и
секреты: медленно, и файл легко случайно попадёт в образ через `COPY .`.
*Критерий 100%: что такое context + и медленно, и небезопасно.*

**A20.** Субъект прямо запрещает. Практически: `latest` — просто имя тега,
никакой гарантии свежести, и оно переезжает на другой образ. Сборка перестаёт
быть воспроизводимой, «работало вчера — сломалось сегодня» без единой правки.
*Критерий 100%: обе причины + «latest не значит новейший».*

**A21.** Debian 13 (trixie) — текущая stable (с августа 2025), значит
предпоследняя — Debian 12 (bookworm). Проверяется на debian.org/releases. Ответ
меняется с каждым релизом Debian, примерно раз в два года, — это не константа
проекта, а вычисляемое значение.
*Критерий 100%: bookworm + обоснование через текущую stable + «пересчитывается».*

**A22.** `--no-install-recommends` не тянет рекомендованные пакеты — меньше вес и
меньше поверхность атаки. `DEBIAN_FRONTEND=noninteractive` не даёт debconf
спрашивать: у сборки нет TTY, вопрос повесил бы её. Как `ARG` — потому что `ENV`
осталась бы в образе и повлияла бы на `apt` в рантайме и на все дочерние процессы.
*Критерий 100%: обе причины + аргумент ARG против ENV.*

## Блок C — PID 1, сигналы, entrypoint

**A23.** `exec` не создаёт новый процесс, а замещает образ текущего процесса
новой программой (системный вызов `execve`). PID сохраняется. Был shell с PID 1 —
стал mysqld с PID 1.
*Критерий 100%: замещение, а не порождение + PID сохраняется + execve.*

**A24.** (1) Docker шлёт SIGTERM процессу с PID 1 — то есть `sh`. (2) `sh` не
имеет обработчика и не пересылает сигнал детям, mysqld ничего не получает.
(3) Docker ждёт grace period, по умолчанию 10 секунд. (4) По таймауту шлёт
SIGKILL, который не перехватывается, — умирают все. (5) mysqld убит без flush
InnoDB, при следующем старте — восстановление, в худшем случае повреждение.
*Критерий 100%: пять шагов + 10 секунд + последствие для БД.*

**A25.** Проблема, которую им закрывают: PID 1 завершился, потому что демон
ушёл в фон, и контейнер тут же умер. `tail -f /dev/null` подвешивает контейнер
фиктивным процессом. Но тогда PID 1 — не демон: сигналы идут не туда, статус
контейнера не отражает состояние сервиса, упавший демон не приводит к
перезапуску. Настоящее решение — foreground-режим демона.
*Критерий 100%: названа исходная проблема + минимум два последствия костыля + правильное решение.*

**A26.** По умолчанию nginx демонизируется: мастер форкается, оригинальный
процесс выходит. В контейнере это выход PID 1 — контейнер останавливается.
`-g "daemon off;"` подставляет директиву конфига, мастер остаётся на переднем
плане и остаётся PID 1.
*Критерий 100%: поведение по умолчанию + «выход PID 1 = стоп контейнера» + что делает флаг.*

**A27.** Завершившийся процесс остаётся в таблице как зомби, пока родитель не
прочитает его статус через `wait()`. Осиротевшие процессы наследуются PID 1, и
он обязан их пожинать, иначе таблица процессов переполняется. Для nginx, mysqld
и php-fpm это не проблема: они полноценные менеджеры процессов и жнут своих
детей. Проблема возникает, когда PID 1 — примитивный shell-скрипт; тогда нужен
init вроде `tini` (или `docker run --init`).
*Критерий 100%: механизм зомби + обязанность PID 1 + вывод «здесь не нужно» с обоснованием.*

**A28.** `docker exec <контейнер> cat /proc/1/comm` (или `ps -p 1 -o comm=`, если
в образе есть `ps` — в slim-образах его часто нет, поэтому `/proc` надёжнее).
*Критерий 100%: рабочая команда + понимание, что ps может отсутствовать.*

**A29.** (1) `exec демон` в конце скрипта — скрипт замещается демоном, тот
получает PID 1. (2) `демон &` плюс `wait` — демон остаётся ребёнком, PID 1 у
скрипта, сигналы приходят скрипту и надо писать обработчики-трансляторы.
Первый способ проще и правильнее; второй нужен, только если PID 1 должен пережить
демона.
*Критерий 100%: оба способа + различие по сигналам + когда какой.*

**A30.** Контейнер перезапускается штатно: при `restart`, при `restart:
on-failure` после падения, при пересоздании из нового образа. Неидемпотентный
entrypoint на втором старте попытается заново создать БД или переустановить
WordPress — в лучшем случае ошибка и crash-loop, в худшем затирание данных.
Поэтому нужен маркер «уже сделано» на **томе**, а не в образе.
*Критерий 100%: перезапуск — норма + конкретный ущерб + маркер на томе.*

## Блок D — Сеть

**A31.** (1) На user-defined bridge работает встроенный DNS по именам
контейнеров/сервисов; на `docker0` — нет (там исторически были `links`).
(2) Изоляция: сети между собой разделены, и подключение к сети явное. Плюс на
дефолтном бридже все контейнеры хоста видят друг друга.
*Критерий 100%: DNS + изоляция.*

**A32.** `127.0.0.11:53`. Docker при старте контейнера подкладывает в его
`/etc/resolv.conf` строку `nameserver 127.0.0.11`; запросы на этот адрес
перехватываются в сетевом namespace контейнера и обрабатываются демоном, который
знает имена и IP всех участников сети. Проверяется `cat /etc/resolv.conf`.
*Критерий 100%: адрес + механизм через resolv.conf + как проверить.*

**A33.** `wordpress` — имя сервиса, встроенный DNS резолвит его в текущий IP
контейнера. IP выдаёт IPAM Docker'а из пула сети, и он меняется при пересоздании
контейнеров и при изменении порядка старта. Захардкоженный IP отработает ровно до
первого `down`/`up` и сломается молча — 502 без внятной причины.
*Критерий 100%: DNS по имени + IP динамический + конкретная поломка.*

**A34.** `links` добавляли записи в `/etc/hosts` контейнера и импортировали
переменные окружения связанного контейнера. Механизм односторонний, требовал
порядка запуска, ломался при перезапуске и работал только на дефолтном бридже.
Устарел, потому что встроенный DNS на user-defined сети решает ту же задачу лучше.
Запрет ничего не отнимает.
*Критерий 100%: что делали технически + минимум два недостатка + чем заменены.*

**A35.** Контейнер не получает свой сетевой namespace, а разделяет namespace
хоста: нет veth, нет NAT, нет изоляции. `localhost` внутри — это loopback хоста,
два контейнера не могут занять один порт. Конкретно для MariaDB: `bind-address =
0.0.0.0` означал бы, что 3306 слушается на всех интерфейсах **хоста**, то есть
база доступна из сети напрямую, минуя nginx.
*Критерий 100%: разделяемый namespace + минимум два следствия + конкретика по MariaDB.*

**A36.** `expose` — метаданные, ничего не открывает. `ports:` создаёт правило
DNAT в цепочке `DOCKER` таблицы `nat`: пакет на порт хоста переписывается на
IP:порт контейнера, плюс правила FORWARD, разрешающие проход. Проверяется
`iptables -t nat -L DOCKER -n`.
*Критерий 100%: DNAT + названы таблица/цепочка + как посмотреть.*

**A37.** veth pair — пара виртуальных интерфейсов, работающих как труба: всё,
что вошло в один конец, выходит из другого. Один конец (`eth0`) кладётся в
сетевой namespace контейнера, второй остаётся на хосте и подключается к
bridge-интерфейсу. Бридж работает как L2-коммутатор между всеми такими концами.
*Критерий 100%: пара как труба + концы в разных namespace + бридж как коммутатор.*

**A38.** Нет. У контейнера вне сети нет интерфейса в этот бридж, маршрута до его
подсети тоже нет, а порт не опубликован на хост, так что и обходного пути через
хост не существует. Достучаться можно, только подключившись к сети
(`docker network connect`).
*Критерий 100%: нет + причина через отсутствие интерфейса/маршрута + порт не опубликован.*

**A39.** `docker network inspect inception-network` — покажет подсеть, шлюз и
секцию `Containers` с именами и IP. Дополнительно: `docker exec nginx getent
hosts mariadb` — проверка резолва по имени.
*Критерий 100%: команда + что именно она показывает.*

**A40.** Правило: публиковать наружу только то, что обязано быть доступно
снаружи. Субъект требует единственную точку входа на 443, поэтому `ports:` только
у nginx. MariaDB и PHP-FPM доступны лишь изнутри сети — это и есть граница
безопасности, не «пароль на базе».
*Критерий 100%: правило + требование субъекта + мысль «изоляция сетью, а не только паролем».*

## Блок E — Хранение

**A41.** **Named volume** — объект Docker с именем и драйвером; создаётся и
удаляется Docker'ом, переживает контейнер, при первом использовании заполняется
из образа. **Bind mount** — произвольный путь хоста; не объект Docker, живёт
своей жизнью, ничем не управляется. **tmpfs** — в памяти, исчезает вместе с
контейнером.
*Критерий 100%: три типа + жизненный цикл каждого.*

**A42.** Это просто путь. Следствия: (1) не виден в `docker volume ls` и не
удаляется через `docker volume rm` / `down -v`; (2) владелец, права и SELinux-метки
берутся с хоста, что даёт «permission denied» на другой машине; (3) путь создаётся
молча, опечатка даёт пустой каталог вместо ошибки; (4) нельзя подключить
драйвер (NFS, облачный диск). Плюс он привязывает compose-файл к раскладке ФС
конкретной машины.
*Критерий 100%: три следствия из перечисленных.*

**A43.**
```yaml
volumes:
  mariadb-data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /home/akuzmin/data/mariadb
```
*Критерий 100%: точный YAML со всеми тремя опциями.*

**A44.** По сути — наличием объекта тома. Здесь Docker создаёт именованный volume
со своим жизненным циклом: он в `docker volume ls`, его сносит `down -v`, на него
ссылаются по имени, и compose-файл не знает про раскладку ФС (путь задан один раз
в определении тома). Запрещённый вариант — анонимное монтирование пути прямо в
сервисе, без объекта. Совпадает только то, что байты в обоих случаях лежат в том
же каталоге.
*Критерий 100%: «объект против пути» + минимум два практических различия + признание, что данные лежат одинаково.*

**A45.** `type: none` + `o: bind` — это опции системного вызова `mount` для
привязки существующего каталога; создавать его драйвер не станет. Обычный bind
mount Docker создал бы сам, а здесь `up` падает с «no such file or directory».
Решено целью `setup` в Makefile (`mkdir -p`), от которой зависит `all`.
*Критерий 100%: почему не создаётся + текст ошибки или её суть + где решено.*

**A46.** Docker копирует в пустой том содержимое образа по этой точке
монтирования. Для MariaDB это была реальная ловушка: пакет `mariadb-server`
выполняет `mysql_install_db` при сборке и оставляет ~113 МБ в `/var/lib/mysql`
внутри образа. «Пустой» том поднимался уже с каталогом `mysql/`, скрипт
инициализации считал его инициализированным, пропускал создание БД и
пользователя — и WordPress получал `Host ... is not allowed to connect`. Лечится
очисткой `/var/lib/mysql` в Dockerfile.
*Критерий 100%: правило заполнения из образа + конкретная ловушка + лечение.*

**A47.**

| | `make down` | `make fclean` |
|---|---|---|
| контейнеры | удалены | удалены |
| образы | сохранены | удалены |
| данные тома | **сохранены** | **уничтожены** |

`fclean` делает `down -v`, а так как тома привязаны к `/home/akuzmin/data`,
содержимое каталога тоже исчезает. Отката нет.
*Критерий 100%: таблица верна + понимание, что `-v` — это и есть разница.*

**A48.** NGINX отдаёт статику и ему незачем писать. При компрометации NGINX
(уязвимость, кривой конфиг с загрузкой) атакующий не сможет записать в
`/var/www/html` файл `shell.php` — а именно он и был бы выполнен PHP-FPM, потому
что тот монтирует тот же том на запись. Это разрыв цепочки «запись файла →
выполнение кода».
*Критерий 100%: нет нужды писать + названа атака «залить .php и выполнить» + принцип наименьших привилегий.*

## Блок F — Секреты и конфигурация

**A49.** (1) `docker inspect <контейнер>` печатает все переменные открыто.
(2) `docker compose config` печатает их. (3) Наследуются каждым дочерним
процессом, видны в `/proc/<pid>/environ` любому, кто может читать этот файл.
(4) Заданные через `ENV` в Dockerfile — впекаются в слой, достаются
`docker history`. Плюс попадают в дампы падений и в логи, которые печатают
окружение.
*Критерий 100%: четыре канала с названными командами.*

**A50.** Файл в `/run/secrets/<имя>`, только на чтение. В **Swarm** секрет
передаётся по зашифрованному raft-логу и монтируется в tmpfs, то есть на диск
узла не попадает. В **Compose** это read-only **bind mount** файла с хоста —
никакого tmpfs. Проверяется `docker exec <c> grep secrets /proc/mounts`.
*Критерий 100%: путь + различие Swarm/Compose + команда проверки. Ответ «в Compose секреты в tmpfs» — максимум 50%.*

**A51.** Критерий: утечка значения даёт злоумышленнику доступ? В `secrets/` —
пароли, ключи, токены. В `.env` — то, что не даёт доступа само по себе: домен,
имя БД, имена пользователей, заголовок сайта, роли. Имя пользователя не секрет:
без пароля оно бесполезно.
*Критерий 100%: сформулирован критерий + примеры в обе стороны.*

**A52.** `source` исполняет файл как shell-код. Пароль
`WP_ADMIN_PASSWORD=a$(rm -rf /var/www/html)b` или с обратными кавычками выполнит
команду при чтении файла. Плюс сломаются любые пароли с `$`, `;`, кавычками.
Парсинг через `grep`/`cut` оставляет содержимое данными.
*Критерий 100%: «source = исполнение» + конкретный опасный пример + правильный способ.*

**A53.** `git ls-files | grep -E 'secrets/|srcs/\.env$'` — должно быть пусто.
Дополнительно `git status --ignored --short` показывает, что файлы существуют и
именно игнорируются, а не отсутствуют.
*Критерий 100%: команда по индексу (не `git status`) + понимание, что проверяется отслеживание.*

**A54.** Нет. Коммит с паролем остаётся в истории, и `git log -p`, `git show
<hash>`, любой клон и любой форк его достанут. Если было запушено — считать
пароль скомпрометированным. Правильно: **сменить пароль** (первое и обязательное),
затем при необходимости переписать историю (`git filter-repo`, BFG) и
форсированно запушить. Для 42 важнее первое: субъект говорит про credentials
«found in your Git repository», а история — это репозиторий.
*Критерий 100%: «нет» + история сохраняет + ротация пароля как первое действие.*

## Блок G — Сервисы и TLS

**A55.** FastCGI — бинарный протокол между веб-сервером и постоянно работающим
процессом-интерпретатором. Отличия от HTTP: бинарный вместо текстового, поверх
долгоживущего соединения, передаёт не «запрос к сайту», а уже разобранные
переменные окружения CGI (`SCRIPT_FILENAME`, `QUERY_STRING`, ...). nginx не умеет
исполнять PHP — в нём нет интерпретатора, и это осознанное решение: он отдаёт
исполнение отдельному процессу, а сам занимается вводом-выводом.
*Критерий 100%: назначение + минимум два отличия от HTTP + «в nginx нет интерпретатора».*

**A56.** UNIX-сокет — файл в mount namespace одного контейнера. NGINX в другом
контейнере со своим mount namespace его просто не видит; общий у них только
сетевой доступ. Если бы оба сервиса жили в одном контейнере, UNIX-сокет был бы
быстрее (нет TCP-стека), но это нарушило бы «один сервис — один контейнер».
*Критерий 100%: «файл в чужом namespace» + «общая только сеть» + признание, что UNIX-сокет быстрее в одном контейнере.*

**A57.** `ssl_protocols TLSv1.2 TLSv1.3;` — перечисление ровно этих двух
отключает SSLv3, TLS 1.0 и TLS 1.1. Проверка:
```bash
openssl s_client -connect akuzmin.42.fr:443 -tls1_1   # должно упасть
openssl s_client -connect akuzmin.42.fr:443 -tls1_2   # должно соединиться
```
или `make tls-test`. Проверка обязана быть негативной тоже: «1.2 работает» ничего
не доказывает, если 1.1 тоже работает.
*Критерий 100%: точная директива + команда проверки + мысль про негативный тест.*

**A58.** `akuzmin.42.fr` — имя из `/etc/hosts`, а не зарегистрированный домен.
Публичный CA подписывает, только подтвердив владение доменом, чего для локального
имени сделать нельзя в принципе. Самоподписанный сертификат даёт полноценное
шифрование и корректный TLS 1.2/1.3; отсутствует только подтверждение
подлинности третьей стороной — отсюда предупреждение браузера. Для локальной
инфраструктуры это нормальная практика.
*Критерий 100%: почему CA невозможен + «шифрование полноценное, отсутствует только доверие» + предупреждение ожидаемо.*

**A59.** `depends_on` задаёт порядок старта и остановки контейнеров. Он **не**
ждёт готовности сервиса: контейнер считается запущенным, как только пошёл его
entrypoint, а MariaDB в этот момент может ещё десятки секунд выполнять
`mysql_install_db`. Дыра закрыта ограниченным циклом ожидания в `setup.sh`,
который делает настоящий аутентифицированный запрос (`SELECT 1`), а не проверку
открытого порта — порт открывается раньше, чем появляются гранты.
*Критерий 100%: порядок против готовности + почему это дыра + аутентифицированный запрос, а не TCP-проверка.*

**A60.** Субъект требует перезапуск при падении. `on-failure` перезапускает при
ненулевом коде выхода, то есть при падении, и уважает осознанную остановку:
после `docker compose stop` контейнер остаётся стоять. `always` поднимал бы его
обратно, мешая демонстрации. `always` уместен для сервиса, который обязан
подниматься после перезагрузки хоста независимо от того, как он был остановлен;
там же обычно берут `unless-stopped`.
*Критерий 100%: разница по коду выхода + требование субъекта + корректный сценарий для always/unless-stopped.*
