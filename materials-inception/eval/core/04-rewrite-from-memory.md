## Этап 2 — MariaDB

Порядок не случаен: снизу вверх, каждый слой проверяется до того, как на него
что-то ставят.

**Написать:** `Dockerfile`, `conf/mariadb.cnf`, `tools/init.sh` и минимальный
`docker-compose.yml` с одним сервисом.

**Требования, которые надо вспомнить самому:**
- база, тег, почему именно он
- пакет ставится в одном `RUN` с очисткой apt-кеша
- `/var/lib/mysql` в образе должен остаться **пустым** (вспомни, почему)
- `bind-address` — какой и почему
- инициализация только на пустом томе, маркер завершения
- временный инстанс без сети
- пароли из `/run/secrets/`, не из окружения
- последняя строка — `exec`

**Проверка:**
```bash
docker compose -f srcs/docker-compose.yml up --build -d
docker logs mariadb | grep -i init
docker exec mariadb cat /proc/1/comm                    # mysqld
docker exec mariadb sh -c 'unset MYSQL_HOST; mariadb --protocol=socket -u root \
    -p"$(cat /run/secrets/db_root_password)" -e "SHOW DATABASES; SELECT user,host FROM mysql.user;"'
```
→ есть база `wordpress` и пользователь `wp_user@%`.

**Если инициализация «пропустилась» на пустом томе** — ты воспроизвёл главный баг
этого проекта. Разберись сам, прежде чем читать разбор: причина в том, что
Docker делает с пустым томом на первом старте.

## Этап 3 — WordPress + PHP-FPM

**Написать:** `Dockerfile`, `conf/www.conf`, `tools/setup.sh`, добавить сервис в
compose.

**Что вспомнить:**
- какие пакеты PHP нужны и зачем каждый
- почему в контейнере нет веб-сервера
- на чём слушает FPM и почему не UNIX-сокет
- почему WordPress скачивается в рантайме, а не в Dockerfile
- ожидание БД: почему `depends_on` недостаточно, почему цикл ограничен, почему
  проверяется запрос, а не открытый порт
- два пользователя, ограничение на имя админа
- владелец файлов после установки
- флаги php-fpm в последней строке

**Проверка:**
```bash
docker exec wordpress cat /proc/1/comm                  # php-fpm8.2
docker exec wordpress wp --path=/var/www/html --allow-root user list
docker exec wordpress ls /var/www/html/wp-config.php
```

## Этап 4 — NGINX и TLS

**Написать:** `Dockerfile`, конфиг nginx, `tools/entrypoint.sh`, добавить сервис.

**Что вспомнить:**
- `ssl_protocols` — точная строка
- откуда берётся сертификат и почему его нет в git
- зачем `subjectAltName`
- как в конфиг попадает домен из `.env`, и какая ловушка ждёт с `envsubst`
- `try_files` для пермалинков
- `fastcgi_pass` — куда и почему по имени
- `fastcgi_param HTTPS on` — зачем
- почему том смонтирован `:ro`
- последняя строка

**Проверка:**
```bash
docker exec nginx cat /proc/1/comm                      # nginx
make tls-test                                            # 1.1 refused, 1.2/1.3 accepted
curl -k -o /dev/null -w "%{http_code}\n" https://akuzmin.42.fr/
```

## Оценка

| результат | вывод |
|---|---|
| написал всё, подглядываний 0–2, все 40 пунктов зелёные | готов |
| написал всё, подглядываний 3–8 | сделай выписки по ним и повтори через неделю |
| подглядываний больше 8, или где-то застрял намертво | материал не усвоен: вернись к `01-theory-questions.md` по проваленной теме |

Записывай не «сколько раз подглядел», а **что** искал. Список вида

```
- точный синтаксис driver_opts для named volume
- флаги php-fpm для foreground
- как в openssl req задать SAN
```

честно показывает, где память кончилась. Синтаксис — не страшно, его смотрят и
на работе. Страшно, если пришлось подглядывать в *структуру* или в *причину*:
это значит, что не понята архитектура, а не забыт флаг.

Только после того, как закончил (или сдался):

- `materials-inception/solutions/core-explained.md` — почему каждое решение такое
- `git diff main..solution/core -- Inception/` — сравнение с эталоном

Сравнивая, ищи не «где у меня по-другому», а **где у меня хуже и почему**.
Другой рабочий вариант — нормально; выбор без причины — нет.
