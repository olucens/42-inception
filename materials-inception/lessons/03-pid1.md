## Прочитай

### Контейнер живёт, пока жив PID 1

Завершился PID 1 — контейнер остановился, остальные процессы внутри убиты. Отсюда всё остальное.

### Почему демон нужно держать на переднем плане

По умолчанию `nginx` уходит в фон: запускает дочерний процесс, а исходный завершается. В контейнере это
завершение PID 1, и контейнер сразу останавливается.

Неправильное «лечение» — подвесить контейнер заглушкой (`tail -f /dev/null`). Контейнер кажется живым, но
демон при этом может давно упасть, и этого никто не заметит. Правильно — запустить демон на переднем плане:

| Сервис | Как |
|---|---|
| nginx | `nginx -g "daemon off;"` |
| php-fpm | `php-fpm8.2 --nodaemonize` |
| mariadb | `mysqld` и так работает на переднем плане |

### Что делает `exec`

```bash
#!/bin/bash
# ...настройка...
exec mysqld --user=mysql
```

`exec` **заменяет** процесс shell на указанную программу, не создавая нового (системный вызов `execve`). PID сохраняется: скрипт был
PID 1, теперь PID 1 — это `mysqld`.

### Что происходит при `docker stop`

Docker шлёт SIGTERM процессу с PID 1, ждёт 10 секунд, затем шлёт SIGKILL.

- **С `exec`:** SIGTERM получает сам демон и аккуратно завершается, сбрасывая данные на диск.
- **Без `exec`:** SIGTERM получает shell. Он не передаёт сигнал дальше, через 10 секунд приходит SIGKILL, и база
  останавливается посреди записи. При следующем старте InnoDB будет восстанавливаться, а в худшем случае данные
  окажутся повреждены.

Есть и особенность ядра: процесс с PID 1 не получает сигнал без обработчика, поэтому простой `sleep` как PID 1
тоже проигнорирует SIGTERM. Демоны обработчики ставят.

### Два способа завершить entrypoint

1. `exec демон`: демон становится PID 1 и сам получает сигналы. Так сделано в проекте.
2. `демон &` плюс `wait`: PID 1 остаётся у скрипта, сигналы приходят ему, и передавать их демону нужно самому
   через `trap`. В Inception это **запрещено**: таблица заканчивает проверку при любом фоновом процессе в entrypoint.

### Зомби

Завершившийся процесс остаётся в таблице процессов, пока родитель не прочитает его статус через `wait()`.
Осиротевшие процессы переходят к PID 1, и он обязан их забирать. nginx, mysqld и php-fpm сами управляют своими
процессами, поэтому в проекте проблемы нет. Для примитивного скрипта в роли PID 1 нужен был бы init вроде `tini`.

### Как построен каждый entrypoint

1. Прочитать настройки и пароли.
2. Выполнить настройку так, чтобы повторный запуск ничего не сломал (**идемпотентность**).
3. `exec` настоящего демона.

Идемпотентность нужна, потому что контейнер перезапускается постоянно: после сбоя, `restart`, пересоздания.
Без неё второй старт попытается заново создать базу или поставить WordPress. В лучшем случае будет ошибка и
бесконечный перезапуск, в худшем потеря данных.

Поэтому признак «уже сделано» хранится на **томе**, а не в образе. MariaDB записывает маркер только после последнего
успешного запроса, так что прерванная настройка просто повторится. WordPress проверяет результат каждого шага.

### Политика перезапуска

| Что произошло | `on-failure` | `unless-stopped` (в проекте) |
|---|---|---|
| `sudo kill -9 <PID на хосте>` | поднимется | поднимется |
| `kill 1` изнутри, выход с кодом 0 | **не поднимется** | поднимется |
| `docker stop` | не поднимется | не поднимется |
| `docker kill` | не поднимется | не поднимется |

Третья политика, `always`, перезапускает при любом выходе, как и `unless-stopped`. Разница в том, что `always` снова
поднимет контейнер после перезапуска демона Docker, даже если ты останавливал его вручную, а `unless-stopped` ручную
остановку помнит.

Запомни две ловушки, которые встречаются на защитах:

- `docker kill` Docker считает ручной остановкой, поэтому контейнер не поднимется ни при какой политике.
- `docker exec X sh -c 'kill -9 1'` ничего не делает: ядро защищает PID 1 от такого сигнала из его же namespace.

## Сделай руками

Нужны образы проекта: `cd ~/42-inception/Inception && make`.

**Шаг 1. Без `exec`:**

```bash
docker run -d --name lab-bad --entrypoint bash nginx:inception -c 'nginx -g "daemon off;"; echo finished'
docker exec lab-bad cat /proc/1/comm          # bash
time docker stop lab-bad                      # около 10 секунд
docker inspect lab-bad -f 'exit={{.State.ExitCode}}'     # 137: убит через SIGKILL
docker rm lab-bad
```

**Шаг 2. С `exec`:**

```bash
docker run -d --name lab-good --entrypoint bash nginx:inception -c 'exec nginx -g "daemon off;"'
docker exec lab-good cat /proc/1/comm         # nginx
time docker stop lab-good                     # почти мгновенно
docker inspect lab-good -f 'exit={{.State.ExitCode}}'    # 0: аккуратно завершился
docker rm lab-good
```

**Шаг 3. Демон ушёл в фон:**

```bash
docker run -d --name lab-quit --entrypoint bash nginx:inception -c 'nginx'
sleep 2; docker inspect lab-quit -f 'running={{.State.Running}} exit={{.State.ExitCode}}'     # false 0
docker rm lab-quit
```

**Шаг 4. Почему запрещён `tail -f`.** Сервиса нет, а контейнер «работает»:

```bash
docker run -d --name lab-fake --entrypoint bash nginx:inception -c 'nginx; tail -f /dev/null'
docker exec lab-fake cat /proc/1/comm         # tail
docker exec lab-fake sh -c 'kill $(cat /run/nginx.pid)'
sleep 2; docker inspect lab-fake -f 'running={{.State.Running}}'     # true, хотя nginx мёртв
docker rm -f lab-fake
```

**Шаг 5. Политика перезапуска на настоящем стеке:**

```bash
for c in mariadb wordpress nginx; do echo "$c: $(docker exec $c cat /proc/1/comm)"; done

docker exec mariadb sh -c 'kill -9 1'; sleep 2
docker inspect mariadb -f 'изнутри kill -9: restarts={{.RestartCount}}'      # 0: ничего не случилось

sudo kill -9 $(docker inspect -f '{{.State.Pid}}' nginx); sleep 6
docker inspect nginx -f 'с хоста kill -9: running={{.State.Running}} restarts={{.RestartCount}}'

docker exec nginx sh -c 'kill 1'; sleep 6
docker inspect nginx -f 'kill 1: running={{.State.Running}} restarts={{.RestartCount}}'

docker kill nginx; sleep 4
docker inspect nginx -f 'docker kill: running={{.State.Running}}'            # false
docker start nginx
```
