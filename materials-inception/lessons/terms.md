## 1. Что такое ядро

Операционная система состоит из двух частей: **ядра** и **обычных программ** вокруг него.

```
программы       nginx, bash, браузер, apt
                  │  системные вызовы: «открой файл», «создай процесс», «отправь данные»
ядро Linux      процессы, память, файлы, сеть, драйверы
                  │
железо          процессор, память, диск, сетевая карта
```

**Ядро** — это тоже программа, но особая. Она загружается первой, работает всё время, пока компьютер включён, и только
ей разрешён прямой доступ к железу. Обычная программа не может сама прочитать диск или отправить пакет: она просит об
этом ядро. Такая просьба называется **системным вызовом**.

Что делает ядро:

- решает, какой процесс сейчас работает на процессоре;
- выдаёт память и следит, чтобы процессы не лезли в чужую;
- читает и пишет файлы;
- принимает и отправляет сетевые пакеты;
- управляет устройствами через драйверы;
- изолирует и ограничивает процессы. На этом построен Docker.

**Debian, Ubuntu и Alpine используют одно и то же ядро Linux.** Различаются в основном программы вокруг него: оболочка,
менеджер пакетов, библиотеки. Отсюда главный вывод для проекта: **в контейнере нет своего ядра**. Образ
`debian:bookworm-slim` — это только файлы программ Debian, а работают они на ядре хоста.

**Как потрогать:**

```bash
uname -r                              # версия ядра, которое работает прямо сейчас
docker run --rm alpine:3.20 uname -r  # то же самое: у контейнера ядро хоста
ls -l /boot/vmlinuz-*                 # само ядро: файл на диске, который загружается при старте
```

## 2. «В Linux всё — файл», но файлы бывают разные

Ты верно услышал, что Linux многое хранит в файлах и показывает через файлы. Уточнение одно: с настройками в `/etc`
работает не ядро, а обычные программы.

| Где | Что это | Кто работает с файлом |
|---|---|---|
| `/etc` | настройки, обычные файлы на диске | программы: nginx читает `/etc/nginx/`, а `/etc/hosts` читает программа, которая ищет адрес по имени |
| `/proc`, `/sys` | **виртуальные файлы**: на диске их нет | ядро создаёт их содержимое в момент чтения, а запись в некоторые меняет его настройки |
| `/dev` | устройства в виде файлов | ядро передаёт чтение и запись драйверу |
| `/var`, `/home` | данные, обычные файлы | программы; база MariaDB лежит в `/var/lib/mysql` |

То есть `/proc` и `/sys` — это окно в память ядра, а не настоящие файлы:

```bash
ls -l /proc/version              # размер 0
cat /proc/version                # но текст есть: его выдаёт ядро
cat /proc/sys/kernel/ostype      # настройка ядра
grep MemTotal /proc/meminfo      # сколько памяти видит ядро
ls /sys/class/net                # сетевые интерфейсы
```

Так работает и Docker: лимит памяти он задаёт записью в файл `memory.max` в `/sys/fs/cgroup`, а ядро выполняет этот лимит
(урок 1).

## 3. OverlayFS и слои

**OverlayFS** — это файловая система в ядре, которая показывает несколько обычных папок как одну.

Представь стопку прозрачных плёнок: сверху видно всё, что на них нарисовано. Плёнки снизу менять нельзя, рисовать можно
только на верхней.

```
merged   то, что контейнер видит как /          /bin  /etc/profile(новый)  /new.txt
           ▲ собирается из папок ниже
upper    записываемый слой контейнера           /etc/profile(новый)  /new.txt  /etc/motd(whiteout)
lower    слои образа, только чтение             /bin  /etc/profile  /etc/motd
```

**Слой — это просто папка на диске с изменёнными файлами.** Ничего более хитрого в нём нет.

| Что делает контейнер | Что происходит |
|---|---|
| читает файл | берётся самая верхняя версия |
| создаёт файл | файл появляется в upper |
| меняет файл из образа | файл копируется в upper и меняется там (**copy-on-write**) |
| удаляет файл из образа | в upper появляется метка **whiteout**, оригинал в lower остаётся |

Сто контейнеров из одного образа используют одни и те же папки lower, поэтому занимают мало места и запускаются быстро.
У каждого своя только папка upper, и она удаляется вместе с контейнером.

**Как увидеть.** Запусти контейнер и измени в нём три файла:

```bash
docker history alpine:3.20                # из чего собран образ
docker run -d --name ov-demo alpine:3.20 sleep 300
docker exec ov-demo sh -c 'echo hi > /new.txt; rm /etc/motd; echo more >> /etc/profile'
docker diff ov-demo                       # A добавлен, C изменён, D удалён
```

Теперь найди папки этих слоёв. Контейнер сам показывает, из чего собран его `/`:

```bash
docker exec ov-demo grep ' / ' /proc/mounts            # overlay, lowerdir=..., upperdir=...
UP=$(docker exec ov-demo grep ' / ' /proc/mounts | tr ',' '\n' | sed -n 's/^upperdir=//p')
LOW=$(docker exec ov-demo grep ' / ' /proc/mounts | tr ',' '\n' | sed -n 's/.*lowerdir=//p')
sudo ls -l "$UP" "$UP/etc"         # new.txt, profile и motd: тип "c" и номер 0, 0, это whiteout
sudo ls -l "${LOW##*:}/etc/motd"   # оригинал в нижнем слое на месте
docker rm -f ov-demo
sudo ls "$UP"                      # No such file or directory: записываемый слой удалён
```

В `lowerdir` папки перечислены через двоеточие сверху вниз. Самая верхняя — служебный слой Docker, а самая нижняя у
`alpine:3.20` — единственный слой образа.

Во многих статьях советуют смотреть `docker inspect -f '{{.GraphDriver}}'`. На свежем Docker 29 эта команда для
контейнера и образа ничего не показывает, потому что слоями управляет containerd. Способ через `/proc/mounts` работает.

Собрать overlay своими руками можно в [уроке 1, шаг 6](01-containers.md).
