# Bonus — почему сделано именно так

Разбор ветки `solution/bonus`. Она собрана **поверх** `solution/core`, поэтому
`git diff solution/core..solution/bonus` показывает ровно бонусную часть и ничего
больше.

Первое, что надо помнить: субъект оценивает бонус, только если обязательная
часть выполнена **идеально**. Поэтому главное правило всей этой ветки — бонус не
имеет права ослабить core.

---

## 0. Список бонусов и что выбрано

| # | Требование субъекта | Реализация | Свой том? |
|---|---|---|---|
| 1 | redis cache для WordPress | `redis` + drop-in объектного кеша | нет |
| 2 | FTP-сервер на том WordPress | `ftp` (vsftpd) | общий с WordPress |
| 3 | статический сайт, **не** PHP | `static` (HTML/CSS/JS + свой nginx) | нет |
| 4 | Adminer | `adminer` (php-cli + встроенный сервер) | нет |
| 5 | сервис на свой выбор | `backup` (mariadb-dump по cron) | **да** |

Субъект: «each service will run inside its own container and will have, **if
necessary**, its dedicated volume». Фраза «if necessary» — это не формальность,
её проверяют вопросом «почему у redis нет тома?». Ответ должен быть по существу,
а не «не понадобилось».

---

## 1. Три правила, которым подчинена вся ветка

**Бонус не открывает второй путь к сайту.** Субъект разрешает «you may open more
ports to suit your needs», и порты 8080/8081/21 этим и оправданы. Но ни один из
них не ведёт к WordPress: статика — отдельный сайт, Adminer — отдельное
приложение, FTP — файловый доступ. NGINX на 443 остаётся единственным входом
именно к сайту.

**Бонус не может уронить core.** Если redis недоступен, WordPress обязан
отдавать страницы — просто без кеша. Если backup не смог снять дамп, стек всё
равно поднимается. Кеш, способный положить сайт, хуже отсутствия кеша.

**Правила core действуют и здесь.** Пин базового образа, `exec` демона в PID 1,
секреты файлами, никаких `latest`. Линтер `tests/check_inception_rules.sh` на
этой ветке проверяет и бонусные сервисы тоже — 71 проверка, 0 провалов.

## 2. Redis — «properly manage the cache»

### Какую задачу он решает

У WordPress **есть** объектный кеш из коробки, но он *непостоянный*: живёт в
памяти PHP в пределах одного запроса и выбрасывается. Каждый просмотр страницы
заново выполняет одни и те же запросы к `wp_options`, `wp_postmeta`, `wp_terms`.

Persistent object cache backend хранит эти результаты **между** запросами, в
общем для всех воркеров PHP-FPM хранилище.

### Ключевая часть — не плагин, а политика вытеснения

Формулировка субъекта «in order to **properly manage** the cache» именно про это:

```
maxmemory 256mb
maxmemory-policy allkeys-lru
```

Почему не дефолт `noeviction`: заполнившись, Redis начинает отвечать на запись
ошибкой OOM. WordPress тогда пишет ошибки в лог вместо кеширования.

Почему не `volatile-lru`: он вытесняет только ключи с TTL, а WordPress пишет
много записей без него. Redis забился бы невытесняемыми ключами и всё равно
вернул OOM.

`allkeys-lru` — вытеснять наименее давно использованный ключ из **любых**. Для
кеша это единственно верный выбор: любое значение можно пересчитать из MariaDB.

### Почему нет тома

Всё содержимое выводится из MariaDB, которая и есть источник истины. Персистить
кеш — ничего не выиграть и заплатить реальным вводом-выводом (RDB форкает
процесс, AOF пишет каждую мутацию). Поэтому `save ""` и `appendonly no`.

Это и есть ответ на «if necessary».

### Почему `protected-mode no`

Без пароля protected-mode отвергает все не-loopback подключения — WordPress не
подключился бы. Граница здесь сетевая: 6379 объявлен через `expose`, наружу не
опубликован, достучаться может только контейнер в `inception-network`.

Честный компромисс, и говорить о нём надо самому: любой контейнер этой сети
читает кеш. Для этого стека приемлемо (кеш хранит результаты запросов, не
учётные данные), а лечится `requirepass` из секрета плюс `WP_REDIS_PASSWORD` в
wp-config.

### Три шага, без которых кеш не работает

Частая ошибка — установить плагин и решить, что готово. Нужно всё три:

1. **Расширение PHP.** `php8.2-redis` в образе WordPress. Без него плагин
   загрузится и покажет «not connected» — в PHP просто нечем говорить по
   протоколу Redis.
2. **Константы до включения.** `WP_REDIS_HOST` должна существовать в
   `wp-config.php` **раньше**, чем включён drop-in: `object-cache.php` читает её
   при загрузке и без хоста молча уходит на `127.0.0.1`, где внутри контейнера
   нет ничего.
3. **`wp redis enable`.** Именно эта команда копирует `object-cache.php` в
   `wp-content/` как **drop-in**. Установка и активация плагина сами по себе не
   меняют ничего.

Проверка:

```bash
make redis-status
# Status: Connected · Drop-in: Valid
# keyspace_hits растёт при обновлении страницы
```

`Drop-in: Valid` — та строка, которая доказывает, что кеш реально включён.

## 3. FTP — vsftpd на том WordPress

Монтируется **тот же** named volume `wordpress-data`, на запись. Файл, залитый
по FTP, немедленно отдаётся сайтом — это проверяется сквозным тестом:
upload → виден в контейнере wordpress → отдан nginx по HTTPS.

### Пассивный режим обязателен

В **активном** режиме сервер сам открывает соединение данных *к клиенту*. Сервер
здесь за NAT Docker'а с приватным адресом — такое соединение не установится.

В **пассивном** клиент открывает оба соединения, что через NAT работает.

Диапазон портов должен совпадать в трёх местах: `pasv_min_port`/`pasv_max_port`
в конфиге, `ports:` в compose и то, что реально доступно. Сервер называет
клиенту порт из диапазона; если он не проброшен — управляющий канал работает,
а любая передача виснет. Симптом «логин прошёл, LIST висит» — это всегда он.

`pasv_address` подставляется в рантайме: контейнер не может узнать адрес хоста
сам, а неверное значение даёт ровно тот же симптом.

### chroot

Без `chroot_local_user=YES` аутентифицированный пользователь ходил бы по всей
файловой системе контейнера — включая `/run/secrets`.

`allow_writeable_chroot=YES` нужен потому, что vsftpd отказывается делать chroot
в каталог, доступный пользователю на запись (известный вектор повышения
привилегий). Здесь запись — вся суть сервиса, поэтому проверка отключена
осознанно. Остаточный риск ограничен: chroot — это том внутри контейнера, где
больше ничего нет.

### Права

Том принадлежит `www-data` (uid 33), потому что в него пишет PHP-FPM. FTP-юзер
добавлен в эту группу плюс `g+w`. Отдать ему владение вместо этого — сломать
загрузки в WordPress.

### Баг №4: vsftpd не может писать в `/dev/stdout`

Обычная контейнерная идиома здесь ломается:

```
500 OOPS: failed to open vsftpd log file:/dev/stdout
```

Причина: vsftpd открывает лог из процесса с разделёнными привилегиями, а
`/dev/stdout` — симлинк на `/proc/self/fd/1`, где «self» это тот процесс, а не
PID 1. Открытие падает, и сервер отвергает соединение **до баннера**.

Лечение: симлинк на `/proc/1/fd/1` — это stdout именно PID 1, то есть тот поток,
который захватывает Docker, и он не зависит от того, кто открывает.

### Баг №5: PAM отвергает shell `nologin`

Логин падал с голым `530 Login incorrect` — ни намёка, что пароль верный.

Причина: `/etc/pam.d/vsftpd` в Debian заканчивается на
`auth required pam_shells.so`, который отвергает пользователя, чей shell не
перечислен в `/etc/shells`. Мы намеренно дали `nologin`.

Лечение: добавить `/usr/sbin/nologin` в `/etc/shells`. Свойство безопасности
сохраняется — интерактивную сессию через ssh или su аккаунт всё равно не
получит, ему разрешено только аутентифицироваться для FTP.

Урок общий: «login incorrect» в FTP/SSH почти никогда не про пароль. Смотри PAM.

## 4. Статический сайт — не PHP

Субъект: «in the language of your choice **except PHP**».

Ограничение — на **сайт**, а не на сервер. Сайт: HTML + CSS + немного ванильного
JS, без сборки и без фреймворка.

**Почему отдаёт nginx.** Отдача статики — ровно то, в чём nginx лучше всего:
`sendfile()` напрямую из page cache в сокет, правильные MIME-типы, условные
запросы. Альтернатива (`python3 -m http.server` или маленький Node-сервер)
добавила бы интерпретатор и более медленный однопоточный сервер, чтобы делать
строго меньше.

Это **отдельный** контейнер nginx со своим образом, конфигом и портом, а не
второй сервис, впихнутый в существующий.

**Почему нет тома.** Сайт — неизменяемый контент, принадлежащий версии образа.
Контраст с WordPress, чей контент — пользовательские данные, и потому живёт на
томе. Хорошая пара для ответа на защите.

## 5. Adminer

**Почему php-cli, а не php-fpm.** FPM говорит по FastCGI, а значит требует
веб-сервер перед собой. Это означало бы либо второй процесс в контейнере (и
тогда нужен супервизор, и PID 1 перестаёт быть сервисом), либо целый
дополнительный контейнер nginx ради одного админского скрипта. `php-cli` даёт
встроенный HTTP-сервер: один процесс, говорит по HTTP напрямую.

**Честный компромисс, который надо назвать самому.** Встроенный сервер PHP
однопоточный и документирован как непригодный для продакшена. Именно здесь это
приемлемо: инструмент на одного оператора, на внутреннем порту, используется
интерактивно несколько минут. Для самого сайта WordPress это было бы
неприемлемо — поэтому там PHP-FPM за nginx.

**Про «except PHP».** Это ограничение относится к бонусу со статическим сайтом.
Adminer — PHP-приложение по определению, и субъект просит его по имени. PHP здесь
обязателен, а не нарушение.

**Почему нет ни тома, ни секретов.** Adminer не хранит состояния, а учётные
данные вводятся в его форму логина. Вписать их в образ — положить пароль в слой.

Сервер при логине — `mariadb`, то есть **имя сервиса**, не IP и не `localhost`.

## 6. Backup — сервис на свой выбор

Здесь спрашивают обоснование, и оно должно быть про риск, а не про «полезно».

### Обоснование

Обязательный стек защищает ровно от одного отказа: **потери контейнера**.
Именованные тома переживают `docker rm`, пересборку образа и перезапуск. Больше
они не защищают ни от чего:

- `make fclean` удаляет тома. Одна команда, без подтверждения.
- `UPDATE` без `WHERE` добросовестно сохраняется.
- Плагин или неудачное обновление WordPress портит таблицы — том исправно
  хранит порчу.
- Диск под `/home/akuzmin/data` умирает.

Том — это **избыточность** против потери контейнера. Бэкап — это **копия на
момент времени**, и только она переживает ошибку. Это другая гарантия, и в стеке
её не было.

### Отвергнутые альтернативы

- **Grafana/Prometheus** — эффектно, но у стека один пользователь и нет истории
  алертинга: получился бы дашборд, который никто не смотрит.
- **Portainer** — готовый образ, здесь запрещён.
- **Почтовый сервер** — ничего в стеке не шлёт почту.

Бэкапы выигрывают, потому что риск, который они снимают, реальный, текущий и в
одной команде от нас.

### Почему отдельный том

`backup-data`, а не `mariadb-data`. Бэкап, лежащий рядом с данными, которые он
защищает, умирает вместе с ними: `down -v`, сбойный диск или неверный путь
заберут оба. Разделение — и есть вся гарантия.

### Детали дампа

`--single-transaction` — снимок в одной транзакции вместо блокировки таблиц.
WordPress продолжает работать во время бэкапа; для InnoDB это правильный выбор.

`--quick` — потоковая выдача строк вместо буферизации целой таблицы в памяти.

Запись в `.part` и `mv` только при успехе: переименование атомарно, поэтому
падение посреди дампа не может оставить обрезанный файл, выглядящий как годный
бэкап.

**Ротация обязательна.** Без неё том растёт, пока не кончится диск, — а полный
диск роняет и MariaDB. То есть бэкап без ротации со временем сам вызывает
аварию, от которой должен был защищать.

### Почему cron — это не костыль

Стоит проговорить точно: `cron -f` — настоящий демон, чья работа — ждать. Запрет
субъекта направлен на **фиктивные** foreground-процессы, существующие только
чтобы контейнер не завершился. Здесь планировщик **и есть** сервис.

### Баг №6: cron не наследует окружение

Cron-задачи запускаются с почти пустым окружением — по сути `HOME`, `PATH`,
`LOGNAME`. Переменные, пришедшие в PID 1 через `env_file:`, в задаче
**отсутствуют**. Это самая частая причина, по которой контейнерный cron «ничего
не делает».

Лечение: entrypoint пишет их в `/etc/backup.env`, скрипт его читает. Пароль туда
**не** попадает — он остаётся в `/run/secrets/db_password`.

Второе следствие: вывод задачи по умолчанию уходит почтой локальному
пользователю, а MTA в контейнере нет. Поэтому в crontab стоит
`> /proc/1/fd/1 2>&1` — иначе лог задачи исчезает бесследно.

Третье: Debian-cron молча игнорирует файлы в `cron.d` с правами группы/мира на
запись или без завершающего перевода строки. Тоже тихий отказ.

### Баг №7: гонка с холодным стартом MariaDB

Первый дамп падал с `ERROR 2002 ... (115)`: `depends_on` упорядочивает старт
контейнеров, а не готовность, и дамп шёл, пока `mysql_install_db` ещё работал.
Хуже то, что cron повторил бы только в 03:00 — оператор нашёл бы пустой
`/backups` без объяснений.

Лечение — тот же ограниченный цикл ожидания с настоящим аутентифицированным
запросом, что и в WordPress.

Замечание, которое стоит знать: на по-настоящему холодном старте первый дамп
может содержать только пустую схему — backup готов чуть раньше, чем WordPress
дописывает таблицы. Это не баг, но `make backup-now` после установки даёт
осмысленный первый дамп.

## 7. Что проверить своими руками

```bash
make re && sleep 130
make ps                      # восемь running
make redis-status            # Connected, Drop-in: Valid, hits растут
make backups                 # хотя бы один .sql.gz
curl -I http://localhost:8080   # статика
curl -I http://localhost:8081   # adminer
curl --ftp-pasv -u ftpuser:PASS ftp://localhost/    # листинг тома WordPress

for c in mariadb wordpress nginx redis ftp static adminer backup; do
  printf "%-10s " $c; docker exec $c cat /proc/1/comm
done
# mysqld php-fpm8.2 nginx redis-server vsftpd nginx php cron
```
