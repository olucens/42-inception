# Core (обязательная часть) — почему сделано именно так

Разбор ветки `solution/core`: каждое решение и причина, по которой оно принято.
Читается вместе с кодом в `Inception/` — там те же объяснения в комментариях,
здесь связная картина.

Правило чтения: сначала попробуй ответить сам, потом сверься.

---

## 0. Три требования, которые определяют всю архитектуру

Всё остальное — следствия.

1. **NGINX — единственный вход, только порт 443, только TLS 1.2/1.3.**
   → у `nginx` есть `ports:`, у остальных только `expose:`.
2. **Свои образы из Debian/Alpine, готовые образы приложений запрещены.**
   → ставим пакеты в голый `debian:bookworm-slim` руками.
3. **Контейнер — не виртуалка, `tail -f` и подобное запрещено.**
   → каждый entrypoint заканчивается `exec` реального демона.

---

## 1. Базовый образ: `debian:bookworm-slim`

**Почему bookworm.** Субъект требует *предпоследнюю* стабильную версию. Debian 13
(trixie) стал stable в августе 2025, значит предпоследняя — Debian 12 (bookworm).
Это надо пересчитывать: когда выйдет Debian 14, правильным ответом станет trixie.

**Почему тег вообще есть.** `latest` запрещён субъектом, но важнее практическая
причина: без явного тега тот же самый Dockerfile через месяц соберёт другой
образ. Сборка перестаёт быть воспроизводимой, и «у меня работало» становится
неотлаживаемым.

**Почему `-slim`.** Меньше пакетов → меньше поверхность атаки и меньше вес.

**Почему Debian, а не Alpine.** Alpine на musl libc; PHP и MariaDB там собираются,
но иногда ведут себя иначе, а отладка glibc-специфичных вещей проще на Debian.
Alpine дал бы образы раза в 3 меньше — это честный аргумент «за», и на защите
нормально сказать «выбрал Debian ради предсказуемости, ценой размера».

## 2. PID 1 — главная идея проекта

Все три entrypoint-скрипта заканчиваются одинаково:

```bash
exec mysqld --user=mysql
exec /usr/sbin/php-fpm8.2 --nodaemonize --force-stderr
exec nginx -g "daemon off;"
```

**Что делает `exec`.** Не порождает новый процесс, а *замещает* образ текущего
процесса. PID сохраняется. Скрипт был PID 1 — теперь PID 1 это демон.

**Почему это критично.** `docker stop` посылает `SIGTERM` именно PID 1, ждёт
10 секунд, потом `SIGKILL`. Обычный `/bin/sh` не пересылает сигналы детям. Без
`exec` цепочка такая: shell (PID 1) получает SIGTERM, игнорирует, mysqld ничего
не получает, через 10 секунд ядро убивает всех через SIGKILL — база падает
посреди записи. С `exec` mysqld получает SIGTERM напрямую и корректно сбрасывает
InnoDB на диск.

**Почему `--nodaemonize` / `daemon off`.** По умолчанию демон форкается и
отсоединяется. Тогда PID 1 (скрипт) завершается — и контейнер умирает мгновенно.
Именно отсюда растут костыли `tail -f /dev/null`: люди «чинят» это, подвешивая
контейнер фиктивным процессом, вместо того чтобы держать демон на переднем плане.
Субъект запрещает костыль, а не проблему: правильное решение — foreground-режим.

Проверка:

```bash
for c in mariadb wordpress nginx; do docker exec $c cat /proc/1/comm; done
# mysqld / php-fpm8.2 / nginx     <- НЕ sh, НЕ bash
```

**Про ENTRYPOINT в exec-форме.** `ENTRYPOINT ["/usr/local/bin/init.sh"]`, а не
`ENTRYPOINT /usr/local/bin/init.sh`. Shell-форма запускает `/bin/sh -c "..."`, и
тогда PID 1 — снова shell, со всеми теми же проблемами.

## 3. Сеть

```yaml
networks:
  inception-network:
    driver: bridge
```

**Что даёт user-defined bridge, чего не даёт дефолтный `docker0`.** Встроенный
DNS-резолвер на `127.0.0.11`, который резолвит *имена сервисов*. Поэтому работает
`fastcgi_pass wordpress:9000` и `MYSQL_HOST=mariadb` — без знания IP. IP выдаёт
IPAM Docker'а, и он меняется между запусками, так что захардкодить его нельзя.

**Почему `links:` запрещены и почему это не потеря.** `links` — механизм эпохи
дефолтного bridge: он писал записи в `/etc/hosts` контейнера. Он устарел ровно
потому, что появился встроенный DNS. Запрет ничего не отнимает.

**Почему `network: host` запрещён.** Контейнер разделил бы сетевой namespace
хоста: никакой изоляции, каждый открытый порт сразу открыт на хосте, и MariaDB
слушала бы 3306 наружу. Вся модель безопасности этого проекта держится на том,
что наружу торчит только 443.

**`expose` против `ports`.**

| | что делает |
|---|---|
| `expose: "3306"` | метаданные + доступность внутри сети. На хост НЕ публикует |
| `ports: "443:443"` | правило DNAT в iptables, порт открыт на хосте |

`ports:` есть только у nginx. Проверка:

```bash
nc -zv localhost 3306   # должно быть refused
nc -zv localhost 9000   # должно быть refused
```

## 4. Тома: named volume, но данные в `/home/login/data`

Два требования субъекта тянут в разные стороны:

- «You must use docker **named volumes**. **Bind mounts are not allowed**»
- «Both named volumes must store their data inside **/home/login/data**»

Обычный named volume лежит в `/var/lib/docker/volumes/...`, а не в `/home`.
Обычный bind mount кладёт куда скажешь, но он запрещён.

Решение — `local` driver с bind-опциями:

```yaml
volumes:
  mariadb-data:
    driver: local
    driver_opts: { type: none, o: bind, device: /home/akuzmin/data/mariadb }
```

Это **настоящий named volume**: объект Docker, виден в `docker volume ls`,
удаляется через `docker volume rm` и через `down -v`. Просто его backing store —
выбранный каталог.

А вот так — запрещённый bind mount (нет объекта тома, не виден в `volume ls`):

```yaml
services:
  mariadb:
    volumes:
      - /home/akuzmin/data/mariadb:/var/lib/mysql   # ← ТАК НЕЛЬЗЯ
```

**Почему `make setup` обязателен.** `o: bind` привязывает *существующий* каталог.
Docker его не создаёт (в отличие от обычного bind mount), и `up` падает с
«no such file or directory». Отсюда `mkdir -p` в Makefile.

**Почему том WordPress смонтирован в nginx как `:ro`.** NGINX отдаёт статику сам,
писать ему незачем. Read-only значит, что скомпрометированный NGINX не сможет
подложить `.php`-файл, который потом выполнит PHP-FPM.

## 5. Секреты против переменных окружения

**Что течёт у переменных окружения:**

- `docker inspect <container>` печатает их открытым текстом;
- `docker compose config` печатает их;
- их наследует каждый дочерний процесс — видно в `/proc/<pid>/environ`;
- заданные через `ENV` в Dockerfile, они впекаются в слой образа, и
  `docker history` их достанет.

**Секрет** — файл, смонтированный read-only в `/run/secrets/<имя>`. Ни в одном из
перечисленных мест его нет.

**Важная деталь для защиты.** В Swarm секреты лежат в tmpfs (в памяти). В Compose
секрет — это read-only **bind mount** файла с хоста. Легко проверить:

```bash
docker exec wordpress grep secrets /proc/mounts
```

Говорить «в Compose секреты в tmpfs» — ошибка, на которой ловят.

**Как разделено в проекте:**

| где | что лежит |
|---|---|
| `srcs/.env` | домен, имя БД, имена пользователей — не тайна |
| `secrets/*.txt` | все пароли |

Оба пути в `.gitignore`. В репозитории только `.env.example`. Субъект:
пароли в git = провал проекта.

**Почему `credentials.txt` парсится через `grep`/`cut`, а не через `source`.**
`source` исполнил бы файл как shell-код: обратная кавычка или `$(...)` внутри
пароля выполнилась бы как команда. Парсинг оставляет файл данными.

## 6. MariaDB

**Почему `bind-address = 0.0.0.0`.** Дефолт Debian — `127.0.0.1`, а внутри
контейнера это его собственный loopback: WordPress не подключится никогда.
`0.0.0.0` — все интерфейсы контейнера, то есть loopback плюс один veth в
inception-network. Наружу это ничего не открывает, потому что порт не
опубликован.

**Почему грант на `'%'`, а не на конкретный IP.** IP контейнера назначает IPAM и
он меняется. Изоляцию даёт сеть, а не хост в гранте.

**Почему временный инстанс с `--skip-networking`.** В момент инициализации у root
ещё нет пароля. `--skip-networking` оставляет только UNIX-сокет, так что за это
окно никто из сети не подключится.

**Почему SQL идёт через stdin, а не через `-e`.** Всё, что после `-p`, видно в
`ps aux` внутри контейнера.

### Баг №1: пакет Debian заранее заполняет `/var/lib/mysql`

`apt-get install mariadb-server` выполняет `mysql_install_db` **во время сборки**
и оставляет в образе ~113 МБ в `/var/lib/mysql`.

Docker при первом использовании **пустого** named volume копирует туда содержимое
образа из точки монтирования. То есть «пустой» том поднимался уже с каталогом
`mysql/` внутри. Скрипт видел его, решал «уже инициализировано», пропускал
создание БД и пользователя — и WordPress вечно получал
`Host '172.x.x.x' is not allowed to connect`.

Лечение в Dockerfile:

```dockerfile
RUN rm -rf /var/lib/mysql/* && mkdir -p /var/lib/mysql && chown -R mysql:mysql /var/lib/mysql
```

Побочный выигрыш: образ легче на 113 МБ.

### Баг №2: `MYSQL_HOST` перехватывает локальный клиент

`.env` задаёт `MYSQL_HOST=mariadb` — это нужно WordPress. Но `env_file:` отдаёт
весь файл **каждому** сервису, включая сам mariadb. Клиентская библиотека
MariaDB читает `MYSQL_HOST` как хост по умолчанию, а указание хоста
переключает транспорт на TCP.

Ловушка: **`--protocol=socket` это не перебивает.** Проверено:

```bash
MYSQL_HOST=mariadb mariadb --protocol=socket --socket=/run/mysqld/mysqld.sock -e 'SELECT 1'
# ERROR 2002 (HY000): Can't connect to server on 'mariadb' (115)
```

А временный инстанс поднят с `--skip-networking`, TCP-слушателя нет вообще.
Лечение — `unset MYSQL_HOST` в начале `init.sh`.

### Почему маркер инициализации — свой файл

Раньше признаком «уже инициализировано» был каталог `/var/lib/mysql/mysql`. Но он
появляется сразу после `mysql_install_db`, то есть **до** создания БД и грантов.
Если SQL-шаг падает, контейнер перезапускается по `restart: on-failure`, видит
каталог и объявляет «всё готово» — получается вечно сломанный сервер.

Теперь `/var/lib/mysql/.inception-initialised` пишется только после последнего
успешного запроса. Незавершённая инициализация корректно повторяется.

## 7. WordPress + PHP-FPM

**Почему в контейнере нет веб-сервера.** Так требует субъект, и это правильно:
одна ответственность на контейнер. PHP-FPM говорит по FastCGI и всё.

**Почему TCP-сокет `0.0.0.0:9000`, а не UNIX-сокет.** UNIX-сокет — это файл в
mount namespace одного контейнера. NGINX в *другом* контейнере его не видит. Общее
у них только сеть.

**Почему WordPress скачивается в рантайме, а не в Dockerfile.** `/var/www/html` —
точка монтирования тома. Docker монтирует том **поверх** каталога, и всё, что туда
положил образ, становится невидимым. Файлы должны появиться после монтирования.

**Почему WP-CLI, а не установка через браузер.** Нужны два пользователя в базе
*до* защиты, без человека с мышкой, и воспроизводимо на чистом томе.

**Почему `--allow-root` и потом `chown`.** WP-CLI отказывается работать от root
без флага. Файлы получаются root'овыми, а воркеры FPM работают от `www-data` —
поэтому в конце `chown -R www-data:www-data`.

**Почему проверка имени админа падает жёстко.** Субъект: имя администратора не
должно содержать `admin`/`administrator`. Узнать об этом на защите — дорого,
поэтому скрипт отказывается стартовать.

**Почему ожидание БД — это цикл, а не `depends_on`.** `depends_on` упорядочивает
только *старт контейнеров*, а не *готовность сервиса*. Контейнер mariadb
«запущен» в момент запуска entrypoint — а впереди ещё `mysql_install_db`.
Нужны оба механизма: `depends_on` для порядка, цикл для готовности.

Цикл делает **аутентифицированный запрос**, а не просто TCP-connect: порт
открывается заметно раньше, чем появляются гранты, и `nc -z` отрапортует
готовность слишком рано. Цикл **ограничен** (120 попыток) и падает с внятной
ошибкой — это не `while true`.

## 8. NGINX и TLS

**Главная строка проекта:**

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

Перечисление ровно этих двух отключает SSLv3, TLS 1.0 и TLS 1.1 (POODLE, BEAST),
которые NGINX иначе бы согласовал.

Проверка — обязательно делать самому:

```bash
make tls-test
# tls1_1   refused
# tls1_2   ACCEPTED
# tls1_3   ACCEPTED
```

**Почему сертификат самоподписанный.** `akuzmin.42.fr` — имя из `/etc/hosts`, а не
реальный домен. Публичный CA не может его подписать в принципе. Предупреждение
браузера ожидаемо; шифрование при этом полноценное.

**Почему сертификат генерируется в рантайме, а не лежит в репозитории.** Приватный
ключ в git — это утёкший ключ. И в слое образа его достанет `docker history`.

**Почему `subjectAltName`.** Современные браузеры игнорируют CN и проверяют имя по
расширению SAN. Без него будет `ERR_CERT_COMMON_NAME_INVALID` вместо обычного
предупреждения о самоподписанном сертификате.

### Баг №3: `http2 on;` не существует в nginx 1.22

Bookworm поставляет nginx 1.22, где HTTP/2 — параметр директивы `listen`.
Отдельная директива `http2 on;` появилась только в 1.25.1, и на 1.22 nginx просто
не стартует:

```
[emerg] unknown directive "http2" in /etc/nginx/nginx.conf:48
```

Правильно для 1.22: `listen 443 ssl http2;`

Мораль: версия базового образа определяет доступный синтаксис конфигов. Пин
образа и синтаксис конфига связаны.

### Почему шаблон + envsubst

`server_name` и CN сертификата должны браться из `.env`. У nginx.conf нет своих
переменных, поэтому рендерим шаблон на старте.

**Тонкость, на которой легко подорваться:** `envsubst` без аргумента заменяет
*каждый* `$NAME`. В конфиге полно переменных самого nginx — `$uri`, `$args`,
`$document_root`, `$fastcgi_script_name` — и все они превратились бы в пустые
строки, тихо породив сломанный конфиг вида `try_files  / /index.php?;`.
Поэтому:

```bash
envsubst '${DOMAIN_NAME}' < template > /etc/nginx/nginx.conf
```

Аргумент ограничивает подстановку одной переменной.

**Почему `nginx -t` перед стартом.** Ошибка конфига видна сразу и внятно, вместо
crash-loop, в котором причина тонет между перезапусками.

**Почему `fastcgi_param HTTPS on`.** TLS терминируется на NGINX, до PHP запрос
доходит открытым. Без этого параметра `is_ssl()` в WordPress ложна, и он
генерирует `http://`-ссылки, которые браузер блокирует как mixed content.

**Почему `try_files $uri $uri/ /index.php?$args`.** Пермалинк `/2026/08/post/` —
не файл на диске. Без этого правила каждая запись отдавала бы 404.

## 9. `restart: on-failure`, а не `always`

Субъект: «containers have to restart in case of a crash». `on-failure`
перезапускает при ненулевом коде выхода — то есть при падении. `always`
перезапускал бы и контейнер, который специально остановили, что мешает
демонстрировать `docker compose stop`.

## 10. Что проверить своими руками перед защитой

```bash
make re                                     # сборка с нуля
make ps                                     # три running
make tls-test                               # 1.0/1.1 refused, 1.2/1.3 accepted
for c in mariadb wordpress nginx; do docker exec $c cat /proc/1/comm; done
nc -zv localhost 3306                       # refused
docker exec wordpress wp --path=/var/www/html --allow-root user list
docker inspect wordpress --format '{{.Config.Env}}' | grep -ci password    # 0
git ls-files | grep -E 'secrets/|srcs/\.env$'                              # пусто
docker exec wordpress wp --path=/var/www/html --allow-root post create \
    --post_title=probe --post_status=publish
make down && make && sleep 30
docker exec wordpress wp --path=/var/www/html --allow-root post list       # probe на месте
```
