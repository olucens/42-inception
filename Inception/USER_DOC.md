# USER_DOC — Inception, user and administrator guide

For the person who runs and operates this stack. No Docker knowledge assumed.
For how it is built, see [DEV_DOC.md](DEV_DOC.md).

---

## 1. What this stack provides

Three services, each in its own container:

| Service | What it does for you | Reachable from |
|---|---|---|
| **nginx** | The web server. Terminates HTTPS and is the only way in. | your browser, `https://akuzmin.42.fr` |
| **wordpress** | The site itself: pages, posts, admin panel, users. | only through nginx |
| **mariadb** | The database, where all the site content lives. | only from wordpress |
| **redis** | Speeds the site up by remembering database answers. | only from wordpress |
| **ftp** | Upload/download site files directly. | your FTP client, port 21 |
| **static** | A separate showcase page, unrelated to WordPress. | <http://localhost:8080> |
| **adminer** | A web page for looking inside the database. | <http://localhost:8081> |
| **backup** | Saves a copy of the database every night. | nothing — it just runs |

Only NGINX is exposed. The database and PHP cannot be reached from your machine
or from the network at all — this is deliberate and is what keeps the site safe.

The site data survives restarts. It lives in `/home/akuzmin/data` on the host:
`mariadb/` (the database) and `wordpress/` (site files, themes, uploads).

## 2. Starting and stopping

Run all commands from the project root (the directory with the `Makefile`).

```bash
make            # build if needed, then start everything
make ps         # what is running
make logs       # follow the logs; Ctrl-C to stop watching
make down       # stop and remove the containers — YOUR DATA IS KEPT
make            # start again; the site is exactly as you left it
```

First start takes a few minutes: images are built, the database is initialised
and WordPress is installed. Later starts take seconds.

**When it is really ready.** `make ps` showing `running` is not enough on the
very first start — WordPress is still installing. Wait for this line:

```bash
make logs | grep wordpress-init
# ... [wordpress-init] starting php-fpm 8.2 as PID 1     <- ready
```

### Danger zone

```bash
make fclean     # DELETES THE DATABASE AND THE WHOLE SITE, PERMANENTLY
```

`make fclean` removes the volumes and wipes `/home/akuzmin/data`. Every post,
page, user and uploaded image is gone and there is no undo. `make down` is what
you want for everyday stopping. Use `fclean` only to prove a clean rebuild works
(`make re`), or when deliberately starting over.

## 3. Reaching the website

The domain must resolve to the machine running the stack. Once per machine:

```bash
echo "127.0.0.1 akuzmin.42.fr" | sudo tee -a /etc/hosts
```

| What | URL |
|---|---|
| Public site | <https://akuzmin.42.fr> |
| Login | <https://akuzmin.42.fr/wp-login.php> |
| Admin panel | <https://akuzmin.42.fr/wp-admin/> |

Always `https://`. There is no `http://` — port 80 is closed on purpose, so a
plain `http://` link will simply fail to connect rather than redirect.

### The browser security warning is expected

You will see "Your connection is not private" / `ERR_CERT_AUTHORITY_INVALID`.

The connection **is** encrypted with TLS 1.2/1.3. The warning is only about *who
vouches for* the certificate: `akuzmin.42.fr` is a private name in your
`/etc/hosts`, not a real internet domain, so no public certificate authority can
ever sign for it. The certificate is generated by the stack itself.

Click **Advanced → Proceed**. In Chrome, if no "Proceed" link appears, click
anywhere on the page and type `thisisunsafe`.

## 4. Credentials

### Where they live

All passwords are in the `secrets/` directory, one file each. This directory is
**excluded from git** and never leaves the machine.

| File | Contains |
|---|---|
| `secrets/db_root_password.txt` | MariaDB `root` password — administrative access to the database |
| `secrets/db_password.txt` | the database password WordPress itself uses |
| `secrets/credentials.txt` | the two WordPress account passwords, as `KEY=value` lines |
| `secrets/ftp_password.txt` | the FTP account password |

`credentials.txt` looks like this:

```
WP_ADMIN_PASSWORD=<the site administrator's password>
WP_USER_PASSWORD=<the second, ordinary user's password>
```

Usernames are *not* secret and live in `srcs/.env`: `WP_ADMIN_USER` (the
administrator) and `WP_USER` (an author-level account).

```bash
grep -E '^WP_(ADMIN_)?USER=' srcs/.env    # who the two accounts are
cat secrets/credentials.txt               # their passwords
```

### Rules

- **Never commit `secrets/` or `srcs/.env`.** `.gitignore` already excludes both.
  A password reaching the repository fails the project outright.
- Keep the files readable only by you: `chmod 600 secrets/*.txt`.

### Changing a password

A WordPress password can be changed from the admin panel (Users → edit → Set New
Password), or from the command line:

```bash
docker exec wordpress wp --path=/var/www/html --allow-root \
    user update siteowner --user_pass='the-new-password'
```

Then update `secrets/credentials.txt` so the file matches reality. Changing that
file alone changes nothing on an already-installed site: it is only read when
WordPress is first installed onto an empty volume.

Changing the **database** passwords is different — they are read on every start,
and the existing database still holds the old ones. Change those only together
with a `make fclean`, i.e. when starting from scratch.

## 5. Checking that things are working

### Quick health check

```bash
make ps
```

All three containers should say `running`. `restarting` means one is crash-looping
— go to §6.

### The site actually answers over HTTPS

```bash
curl -k -o /dev/null -w "%{http_code}\n" https://akuzmin.42.fr/
# 200
```

`-k` skips certificate verification, which is expected for a self-signed
certificate.

### Encryption is TLS 1.2/1.3 only

This is a hard requirement of the project, and it is directly checkable:

```bash
make tls-test
# tls1_1   refused      <- older, broken protocols rejected
# tls1_2   ACCEPTED
# tls1_3   ACCEPTED
```

To see what a browser actually negotiates:

```bash
echo | openssl s_client -connect akuzmin.42.fr:443 2>/dev/null | grep -E "Protocol|Cipher"
```

### The database is genuinely private

Neither of these should connect — that is the point:

```bash
nc -zv akuzmin.42.fr 3306    # database   -> must be refused
nc -zv akuzmin.42.fr 9000    # PHP-FPM    -> must be refused
```

### The two required accounts exist

```bash
docker exec wordpress wp --path=/var/www/html --allow-root user list
# one administrator + one other user
```

### Data really persists

```bash
make down && make
```

The site comes back with all content intact. If it does not, the volumes are not
being reused — see DEV_DOC.md.

## 6. When something is wrong

**Start with the logs.** They name the failing service and usually the reason:

```bash
make logs                       # everything
docker logs nginx --tail 40     # just one
```

| Symptom | Likely cause | Fix |
|---|---|---|
| `make` stops at `ERROR: srcs/.env is missing` | first run on this machine | `cp srcs/.env.example srcs/.env` |
| `ERROR: secrets/....txt is missing` | secrets not created | see §4 and README "Instructions" |
| browser: site can't be reached | domain not in `/etc/hosts`, or stack down | §3, then `make ps` |
| browser: connection refused on `http://` | port 80 is closed by design | use `https://` |
| `502 Bad Gateway` | nginx is up but PHP-FPM is not | `docker logs wordpress` |
| `Error establishing a database connection` | MariaDB not ready or credentials changed | `docker logs mariadb` |
| a container keeps `restarting` | it crashes on start | `docker logs <name>` — the last lines before each restart are the reason |
| port 443 already in use | another web server on the host | stop it, or free the port |

Nothing here is fixed by deleting data. Resist `make fclean` as a first move: it
destroys the site and usually hides the real cause rather than fixing it.

## 7. Using the bonus services

### Redis cache

Nothing to do — it works by itself. To confirm it is actually being used:

```bash
make redis-status
# Status: Connected
# ... keyspace_hits / keyspace_misses
```

`Connected` plus a rising `keyspace_hits` means the cache is doing its job. If it
says not connected, the site still works — just slower. That is deliberate: a
broken cache must never take the site down.

### FTP

Connect with any FTP client (FileZilla, `lftp`, or `curl`) to the host on port
21, as `FTP_USER` from `srcs/.env` with the password from
`secrets/ftp_password.txt`. **Passive mode is required** — active mode cannot
work through Docker's NAT. Most clients use passive by default; FileZilla calls
it "Transfer mode: Passive".

```bash
curl --ftp-pasv -u ftpuser:PASSWORD ftp://akuzmin.42.fr/            # list
curl --ftp-pasv -u ftpuser:PASSWORD -T theme.zip ftp://akuzmin.42.fr/  # upload
```

You land directly in the site root and cannot leave it. A file uploaded here is
served by the website immediately — it is the same volume.

*If login works but listing hangs forever*, passive mode is off or
`FTP_PASV_ADDRESS` in `srcs/.env` is wrong. It must be the address **you** use to
reach the server, not the container's.

### Static site

<http://localhost:8080> — plain HTTP, no login. Unrelated to WordPress; it has
its own web server and shares nothing with the site.

### Adminer

<http://localhost:8081>. Log in with:

| Field | Value |
|---|---|
| System | MySQL |
| Server | `mariadb` |
| Username | `MYSQL_USER` from `srcs/.env` |
| Password | contents of `secrets/db_password.txt` |
| Database | `MYSQL_DATABASE` from `srcs/.env` |

Server is `mariadb` — the *service name*, not an IP and not `localhost`.

Adminer can change and delete data directly, with no undo and no WordPress
validation. Use it to look, not to edit, unless you know exactly what you are
doing.

### Backups

A dump is taken nightly at 03:00 and the 7 most recent are kept.

```bash
make backups        # list what exists
make backup-now     # take one immediately
```

Files land on their own volume at `/home/akuzmin/data/backups`, separate from
the database — a backup stored beside the data it protects is not a backup.

To restore one:

```bash
docker exec backup sh -c 'zcat /backups/wordpress-YYYYMMDD-HHMMSS.sql.gz' \
  | docker exec -i mariadb sh -c 'unset MYSQL_HOST; mariadb --protocol=socket \
      -u root -p"$(cat /run/secrets/db_root_password)"'
```

Restoring **overwrites the current database**. Take a fresh backup first.

*On a very first start the initial dump may be nearly empty* — the backup
service becomes ready slightly before WordPress finishes installing. Run
`make backup-now` once the site is up.
